# XJD Base Directory Specification

Status: draft 0. Modeled on the XDG Base Directory Specification.

XJD is the Costa Decimal System: a Johnny Decimal based way of organizing a
business. This document says where an XJD system, its configuration, and the
tools that check it live on disk. It does not say what the system contains.

The words MUST, SHOULD and MAY mean what they mean in RFC 2119.

## Why this exists

Tools that read or check a CDS (the jdlint mod, a flake or typix rebuild, an
agent) need to find the same files the same way. Without one rule, each tool
invents its own paths.

## Variables

| Variable | Holds | Default if unset or empty |
|---|---|---|
| `XJD_HOME` | The root of one XJD system: the Johnny Decimal tree and its JDex | `$HOME/xjd` |
| `XJD_CONFIG_HOME` | User configuration | `$HOME/.config/xjd` |
| `XJD_STATE_HOME` | Data that should survive restarts but is not configuration, such as the last findings | `$HOME/.local/state/xjd` |
| `XJD_CACHE_HOME` | Disposable data | `$HOME/.cache/xjd` |
| `XJD_CONFIG_DIRS` | Extra config directories, searched after `XJD_CONFIG_HOME`. Colon-separated, most important first | `/etc/xjd` |
| `XJD_DATA_DIRS` | Directories holding checkers and adapters. Colon-separated, most important first | `/usr/local/share/xjd:/usr/share/xjd` |

Rules, the same as XDG:

- Every path in these variables MUST be absolute. A tool MUST ignore a
  relative path.
- A tool that writes a file and finds its directory missing SHOULD create it
  with mode `0700`.
- A tool that reads configuration looks in `XJD_CONFIG_HOME` first, then each
  entry of `XJD_CONFIG_DIRS` in order. The first match wins. Files are not
  merged.
- `XJD_HOME` is a single directory, not a list. A tool works on one system
  at a time.

## Finding the home

A tool finds the system root in this order:

1. `XJD_HOME`, if set to an absolute path that exists.
2. The nearest parent of the current directory that contains an `xjd.toml`.
3. Nothing. The tool is out of scope and MUST do nothing visible. It MUST NOT
   show an empty state.

## Files

```
$XJD_HOME/
  xjd.toml            marks the home; per-system settings
  <the JD tree>       areas, categories, IDs, as the system defines them
  <the JDex>          wherever the system's lint config says

$XJD_CONFIG_HOME/
  xjd.toml            user-wide settings; lower priority than the home's
  checkers/<name>.*   config for one checker (for jdlint, its jdlint.toml)

$XJD_STATE_HOME/
  findings.json       the last findings, in the format below

$XJD_DATA_DIRS/
  checkers/<name>     a checker's executable or adapter
```

Settings are looked up in the home's `xjd.toml` first, then the user's. The
first file that defines a key wins.

### Files that live in the home but are not part of the tree

`xjd.toml` and the checker's own config sit at the top of the home. jdlint
reports any file at that level that matches no allowed format, so both MUST be
in the checker's ignore list (for jdlint, `linter.ignore = ["xjd.toml",
"jdlint.toml"]`). `fixtures/home/jdlint.toml` shows it.

### Configuration is read-only

Tools MUST NOT write to `xjd.toml` or to checker configs. They are meant to be
generated by a flake or typix build and may sit on a read-only store path.
Tools write only to `XJD_STATE_HOME` and `XJD_CACHE_HOME`.

## `xjd.toml`

Only what the first checker needs is defined. Unknown keys MUST be ignored.

```toml
# Optional. Human-readable name of this system.
name = "Costa"

# One table per checker.
[checkers.jdlint]
# Path to the checker's config, relative to the home, or absolute.
config = "jdlint.toml"
# Paths that trigger a run when they change. Relative to the home.
# Globs allowed. Default: the whole home.
watch = ["**"]
# Paths to skip even if they match `watch`.
ignore = [".git/**"]
```

## Checkers

A checker is a command that:

1. Takes the home as its first argument.
2. Reads nothing else it was not given by its config.
3. Never changes files in the home.
4. Prints a JSON array of findings on standard output.
5. Exits 0 when it ran, even if it found problems. A non-zero exit means the
   checker itself failed.

jdlint is the first checker. It does not print this format itself, so a small
adapter turns its `--json` output into findings.

### Finding

```json
{
  "id": "bc8131b8769eae02f4abd9c74ad38ff9",
  "alias": "<the same problem's other ID>",
  "source": "jdlint",
  "code": "DUPLICATE_ID",
  "path": "10-19 Life/11 Me/11.11 Me",
  "message": "11.11 is used more than once",
  "severity": "error"
}
```

- `id`: stays the same for the same problem between runs, so a rename keeps it.
  How it is made: [`proposals/stable-finding-ids.md`](proposals/stable-finding-ids.md).
- `alias`: optional. The ID this problem has when findings stop or start sharing
  its number. To tell whether a problem was seen before, compare with both.
- `source`: the checker's name.
- `code`: the checker's own name for the problem. Not renamed, so it matches
  what the checker prints on its own.
- `path`: relative to the home. May be empty if the problem is not about a
  path.
- `message`: one plain sentence.
- `severity`: `error` or `warning`.

Every consumer reads this one shape: the status strip, the agent's feedback,
and any later flake or typix step.

## Out of scope for this draft

- How a flake or typix rebuild reads findings.
- Fix actions. Checkers only report.
- More than one home at a time.
- Windows and macOS defaults. (XDG-style paths are used everywhere for now.)
